# Module 04 — Terraform

> **Stop clicking around in cloud consoles. Write your infrastructure as code.**

Terraform lets you describe your entire infrastructure — servers, databases, networks, DNS records, load balancers — in files that you version control, review in pull requests, and deploy automatically. If infrastructure lives in a YAML or `.tf` file, it can be audited, rolled back, and reproduced exactly.

This is **Infrastructure as Code (IaC)**.

## 1. Why IaC?

Imagine you manually clicked through the AWS console to:
- Create a VPC with subnets
- Set up security groups
- Launch 3 EC2 instances
- Create an RDS database
- Configure a load balancer

Now you need to:
- Recreate it exactly in a staging environment
- Audit what changed last Thursday
- Roll back a bad network rule
- Let a teammate reproduce your setup

**Without IaC:** You can't. Or at least not reliably.

**With Terraform:** `terraform apply` and it's done. Identically.

## 3. Core Terraform Concepts

### The Terraform Workflow
```
      terraform init
           │
      terraform plan        ← preview changes (read-only, safe to run anytime)
           │
      terraform apply       ← make it real
           │
      terraform destroy     ← tear it all down
```

### Key Concepts

| Term | What it is |
|------|-----------|
| **Provider** | Plugin for a cloud/service (AWS, GCP, Azure, GitHub, Cloudflare...) |
| **Resource** | A piece of infrastructure (an EC2 instance, an S3 bucket, a DNS record) |
| **Data source** | Read existing infrastructure (not create it) |
| **Variable** | Input values (like function parameters) |
| **Output** | Values to export (like function return values) |
| **State** | Terraform's database of what infrastructure currently exists |
| **Module** | Reusable, packaged Terraform configuration |

### HCL Syntax
```hcl
# This is a comment

# Block syntax: type "resource_type" "local_name" { ... }
resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-devops-essentials-bucket"

  tags = {
    Name        = "My Bucket"
    Environment = "dev"
    ManagedBy   = "terraform"
  }
}

# Reference another resource with: resource_type.local_name.attribute
output "bucket_arn" {
  value = aws_s3_bucket.my_bucket.arn
}

# Variables
variable "environment" {
  type        = string
  description = "Deployment environment"
  default     = "dev"
}

# Use a variable with var.variable_name
locals {
  bucket_name = "my-app-${var.environment}"
}
```

## 4. Your First Terraform Configuration

We'll start with something local — no cloud account required. We'll use the `local` provider to create files.

Create `terraform/practice/main.tf`:

```hcl
terraform {
  required_version = ">= 1.0"

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.4"
    }
  }
}

# Create a local file
resource "local_file" "app_config" {
  filename = "${path.module}/output/config.json"
  content  = jsonencode({
    app_name    = "devops-essentials"
    environment = var.environment
    version     = "0.1.0"
    deployed_at = timestamp()
  })
}

resource "local_file" "readme" {
  filename = "${path.module}/output/DEPLOYED.md"
  content  = <<-EOT
    # Deployment Info

    - Environment: ${var.environment}
    - App: devops-essentials
    - Managed by: Terraform

    Do not edit this file manually.
  EOT
}

variable "environment" {
  type    = string
  default = "dev"
}

output "config_file_path" {
  value = local_file.app_config.filename
}
```

```bash
cd terraform/practice

# Step 1: Initialize (downloads providers)
terraform init

# Step 2: Preview changes (always do this first!)
terraform plan

# Step 3: Apply changes
terraform apply         # prompts for confirmation
terraform apply -auto-approve   # skip confirmation (use in CI only)

# Look at what was created
cat output/config.json
cat output/DEPLOYED.md

# Step 4: Change a variable and see the plan
terraform plan -var="environment=staging"

# Step 5: Tear it down
terraform destroy
```

## 5. Understanding Terraform State

After `terraform apply`, Terraform creates `terraform.tfstate`. This is Terraform's database of what exists.

```bash
cat terraform.tfstate
```

You'll see something like:
```json
{
  "version": 4,
  "terraform_version": "1.7.0",
  "resources": [
    {
      "type": "local_file",
      "name": "app_config",
      "instances": [
        {
          "attributes": {
            "filename": "./output/config.json",
            "content": "...",
            "id": "sha1-abc123"
          }
        }
      ]
    }
  ]
}
```

**NEVER commit `terraform.tfstate` to Git.** It contains sensitive data (connection strings, private IPs, passwords). Add to `.gitignore`:
```
*.tfstate
*.tfstate.backup
.terraform/
```

### Remote State

In teams, everyone needs to share the same state file. Use **remote state** instead:

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket"
    key            = "devops-essentials/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-state-lock"  # Prevents concurrent applies
    encrypt        = true
  }
}
```

Or with Terraform Cloud (free for small teams):
```hcl
terraform {
  cloud {
    organization = "your-org"
    workspaces {
      name = "devops-essentials"
    }
  }
}
```

## 6. Variables and Outputs in Depth

Create `terraform/practice/variables.tf`:
```hcl
variable "app_name" {
  type        = string
  description = "Name of the application"
  default     = "devops-app"
}

variable "environment" {
  type        = string
  description = "Deployment environment (dev, staging, prod)"
  
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Environment must be dev, staging, or prod."
  }
}

variable "replica_count" {
  type        = number
  description = "Number of app replicas"
  default     = 2

  validation {
    condition     = var.replica_count > 0 && var.replica_count <= 10
    error_message = "Replica count must be between 1 and 10."
  }
}

variable "tags" {
  type = map(string)
  default = {
    ManagedBy = "terraform"
    Project   = "devops-essentials"
  }
}
```

Ways to provide variable values:

```bash
# 1. Command line flag
terraform apply -var="environment=staging"

# 2. Variable file (commit non-sensitive vars, .gitignore the rest)
terraform apply -var-file="staging.tfvars"

# 3. Environment variable (TF_VAR_ prefix)
export TF_VAR_environment=staging
terraform apply

# 4. Interactive prompt (if no default and no value provided)
terraform apply
#  var.environment
#    Enter a value: staging
```

Create `terraform/practice/staging.tfvars`:
```hcl
environment   = "staging"
replica_count = 3
tags = {
  ManagedBy   = "terraform"
  Project     = "devops-essentials"
  Environment = "staging"
}
```

## 7. Terraform Modules

Modules are reusable packages of Terraform configuration. Think npm packages, but for infrastructure.

```
terraform/
├── main.tf              ← root module
├── variables.tf
├── outputs.tf
└── modules/
    └── app-server/      ← child module
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

Using a module:
```hcl
# In root main.tf
module "web_server" {
  source = "./modules/app-server"    # local module
  
  # Or from Terraform Registry:
  # source  = "terraform-aws-modules/ec2-instance/aws"
  # version = "~> 5.0"

  instance_type = "t3.micro"
  environment   = var.environment
}

output "server_ip" {
  value = module.web_server.public_ip
}
```

## 8. Real Exercise: Provision Cloud Infrastructure (Free Tier)

> **We'll come back to cloud-specific Terraform in the Cloud modules (09, 10). For now, practice the patterns.**

### Exercise A: Local file management
Use Terraform to generate all the Kubernetes YAML manifests for Module 05.

Create `terraform/k8s-manifests/main.tf`:
```hcl
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.4"
    }
  }
}

variable "app_name" { default = "devops-app" }
variable "image" { default = "your-dockerhub-username/devops-app:latest" }
variable "replicas" { default = 2 }
variable "port" { default = 3000 }

resource "local_file" "deployment" {
  filename = "${path.module}/../../k8s/deployment.yaml"
  content  = <<-EOT
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: ${var.app_name}
      labels:
        app: ${var.app_name}
    spec:
      replicas: ${var.replicas}
      selector:
        matchLabels:
          app: ${var.app_name}
      template:
        metadata:
          labels:
            app: ${var.app_name}
        spec:
          containers:
            - name: ${var.app_name}
              image: ${var.image}
              ports:
                - containerPort: ${var.port}
  EOT
}

resource "local_file" "service" {
  filename = "${path.module}/../../k8s/service.yaml"
  content  = <<-EOT
    apiVersion: v1
    kind: Service
    metadata:
      name: ${var.app_name}-service
    spec:
      selector:
        app: ${var.app_name}
      ports:
        - protocol: TCP
          port: 80
          targetPort: ${var.port}
      type: ClusterIP
  EOT
}
```

```bash
cd terraform/k8s-manifests
terraform init && terraform apply -auto-approve
# Check that k8s/deployment.yaml and k8s/service.yaml were created
cat ../../k8s/deployment.yaml
```

### Exercise B: Terraform in GitHub Actions
Create `.github/workflows/terraform.yml`:

```yaml
name: Terraform Plan

on:
  pull_request:
    paths: ["terraform/**"]

jobs:
  terraform:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: terraform/practice

    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.7.0"

      - name: Terraform Init
        run: terraform init

      - name: Terraform Plan
        run: terraform plan -var="environment=staging"

      - name: Terraform Format Check
        run: terraform fmt -check -recursive
```

## 9. Terraform vs Ansible vs Pulumi

| | Terraform | Ansible | Pulumi |
|--|-----------|---------|--------|
| **Language** | HCL | YAML | Python/TypeScript/Go |
| **Focus** | Provisioning infrastructure | Configuring servers | Provisioning infrastructure |
| **State** | Yes (tracks what exists) | No (runs commands) | Yes |
| **Approach** | Declarative | Imperative/Declarative mix | Declarative |
| **Best for** | Creating cloud resources | Installing software, managing files on servers | Teams who prefer a real programming language |

**The rule of thumb:**
- **Terraform** → create the server
- **Ansible** → configure the server
- **Docker/K8s** → run the app
